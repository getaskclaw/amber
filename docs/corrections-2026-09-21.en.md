# Correction notice 2026-09-21: astra's three W36 UI-build "✓" cells were fallback-delivered

> 中文版：[corrections-2026-09-21.md](corrections-2026-09-21.md)

## What is being corrected

In AMBER's published results, the UI-build case A-d9b79b46 for the
**gpt-6-astra-900k @ OpenAI Codex** lane shows "✓" at **low / medium / high** in the
2026-W36 issue and all derived leaderboards. The delivering sessions were actually completed by
the harness's fallback model **glm-5.3-flash @ Ollama Cloud**, not by astra itself. Those three
cells are void.

Consequence: astra's headline on this site's README leaderboard is corrected from **16/23 to
15/23**, moving it from the #3 tie into the #4 tie group.

## How it was found and verified

1. On 09-20/21, at the owner's request, we re-ran astra's full library (medium band, 23 cases,
   28 runs). A-d9b79b46 failed twice (output lacked the required ```vue fence, so the oracle had
   no candidate file to judge) — contradicting the W36 "passed at low/medium/high" record.
2. Ledger audit (session_model_usage records the model and billing lane that **actually
   served**): for the delivering sessions behind those three cells, every main-task row is pinned
   to `glm-5.3-flash @ ollama-cloud` (~8.1K in / 6.8K–8.3K out of real work), while astra appears
   only in `title_generation` (747 in / 21–56 out). In the high-band session even the title was
   generated by glm — zero astra work rows in the entire session.
3. Mechanism: the W36 harness's client-side watchdog killed astra's small-prompt + long
   silent-reasoning requests (a defect only fixed in harness v0.3 — see amber-gpt's W38 issue);
   the fallback then silently completed and submitted the work, and the cell was recorded under
   the lane's name. This is an attribution defect, not deliberate falsification; the same case's
   max/xhigh "no delivery" cells from the same week are the same watchdog's other failure mode.
4. We also falsified the reverse: if astra itself had this capability on the re-test days
   (09-20/21, lane telemetry verified healthy), at least one of the three clean bands should
   pass — instead all four runs across low/medium/high failed with the identical cause,
   corroborating that the W36 cells were not astra's own work.

## What changes

- amber-gpt W36 issue: the three cells (low/medium/high on A-d9b79b46) are voided, pointing to
  this notice and W38 Addendum 5.
- This site's README leaderboard: astra 16/23 → **15/23**, moved out of the #3 tie into the
  #4 tie group.
- nine-axis-top3-2026-09-18: astra's membership in the UI axis "perfect-score tie" is voided
  (astra is removed from that axis's tied list); its other axes (e.g. the #2 tie on attribution)
  are unaffected.
- The completion-matrix figure (docs/images/completion-matrix-7way.png) shows an astra UI cell
  derived from the same substitute cells; regenerating the figure is logged as debt and ships
  with the next matrix update.
- Under review: two A-0676097b variants and A-ea80d793 also show fallback rows in their
  09-05/06 sessions; conclusions will be published separately.

## Process fix

Score attribution no longer trusts the lane label alone: per-issue wire verification gains a
**main-task-row pin** check — the session's main task (not auxiliary jobs like title generation)
must be served by the exact model and billing lane under examination, or the cell records
driver_exception instead of a score.
